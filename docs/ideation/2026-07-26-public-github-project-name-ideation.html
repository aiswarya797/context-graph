What the name must earn

Grounding Context

Codebase Context. The repository currently ships a dependency-free Python apparatus for a pinned, plain-Codex SWE-Explore source-localization baseline. Its public behavior is a strict sequence of preparation, doctor and smoke gates, immutable run capture, official scoring, validation, reporting, and freezing.

The project’s distinctive asset is not a graph. It is the retained evidence behind a benchmark claim: pinned inputs, raw provider events, stderr, telemetry, evaluator provenance, contamination checks, repository isolation, and an explicit claimability decision. The current README also says that CodeGraph, OKFs, retrieval, embeddings, generated context, wiki, and memory are not implemented.

Naming boundary: keep Context Graph as an internal research-program label if useful, but do not use it as the public release name today. The phrase is already occupied by adjacent projects such as Code Context Graph, tae2089/code-context-graph, and Neo4j’s create-context-graph.

The strongest pattern from the reviewed tool repositories—CodexBar, Peekaboo, MCPorter, Oracle, Summarize, agent-scripts, agent-rules, and Aspects—is a compact noun or function word paired with a literal first-line subtitle. The name carries identity; the subtitle carries precision.

Top pick

1. RepoWitness

1

Description: Publish the repository as repo-witness, with the product name RepoWitness and the subtitle “Auditable source-localization benchmarks for coding agents.” “Repo” makes the subject concrete; “Witness” makes retained, inspectable evidence the product promise.

Basis
direct: The current apparatus retains raw execution evidence, validates evaluator and repository provenance, detects contamination, and freezes only claimable runs. external: No indexed product or GitHub collision surfaced for RepoWitness in the naming screen, and the exact PyPI names repowitness and repo-witness returned no project.
Rationale
It is accurate on day one and remains true when plain Codex, CodeGraph, and later approaches become comparison arms. It differentiates the project on trust without claiming that it performs graph retrieval.
Downsides
“Witness” alone would be vague, so the compound and literal subtitle should always travel together. Collision screening is not trademark clearance.

2. RegionWitness

2

Description: Use region-witness when the public identity should foreground the exact output being evaluated: ranked source regions backed by an auditable run record.

Basis
direct: The current protocol is direct-region-v1, and every valid attempt returns ordered evidence regions before official source-localization scoring.
Rationale
The name joins the benchmark’s measured object with its verification contract. It is more technically explicit than RepoWitness and still avoids promising a graph.
Downsides
It is longer, less fluid aloud, and may feel narrow if the project later evaluates non-region outputs.

3. Regionmark

3

Description: Use regionmark for a compact, technical name centered on scoring and validating ranked evidence regions. “Mark” can mean both a selected location and an earned quality mark.

Basis
direct: Source regions are the canonical response unit and are checked through schema validation, official metrics, run validation, and freezing. reasoned: a dual-meaning compound creates identity without introducing an unshipped architecture.
Rationale
It is short, currently unclaimed on PyPI in the screen, and honest about what the benchmark measures.
Downsides
It can sound like a source annotation tool, and “region” may become constraining if the evaluation contract broadens.
